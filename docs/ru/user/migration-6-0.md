# Переход на Vesma 6.0

**🌐 Language / Язык:** [English](../../en/user/migration-6-0.md) · Русский

> Гайд по миграции 5.6.x → 6.0: что ломается, как перенести хранилище командой
> `vesma migrate-store`, как обновить конфиги, окружение, MCP-обвязку и
> Python-импорты. Прочитайте разделы 1–2 до любых действий; сам мовер
> принудительно делает снапшот и по умолчанию работает в режиме dry-run.

Vesma 6.0 — релиз контрактов: ребрендинг, который 5.0 несла как слой
совместимости (старые написания `mnemos` продолжали работать наряду с новыми
`vesma`-именами), теперь завершён на всех поверхностях. Одна команда —
`vesma migrate-store` — переносит хранилище на новую идентичность; всё
остальное — разовые правки конфигов и обвязки. Семантика переноса утверждена
в [ADR-0044](../../project/adr/0044-store-migration.md); эта страница —
пошаговый сценарий для оператора.

---

## 1. Что меняется и почему

Ребрендинг 5.0 переименовал продукт, но сознательно оставил живыми все
старые написания: инструменты отвечали и на `mnemos_*`, и на `vesma_*`,
переменные окружения читались с трёх префиксов, Python-пакет импортировался
под двумя именами, а хранилище на диске жило в исходном доме. 6.0 закрывает
каждое из этих двойных написаний — 6.0 «от начала до конца vesma» на каждой
поверхности, до которой вы можете дотянуться.

Что **не** меняется: ваши записи. Содержимое, метки времени, идентификаторы
и векторы сохраняются побайтово; мовер переписывает только префикс тегов,
слаг проектного пространства, имена файлов и привязки путей в конфиге — и за всем этим стоит
проверенный снапшот (раздел 2).

### Ломающие изменения одним взглядом

| # | Что | 5.6.x | 6.0 | Что делать |
|---|-----|-------|-----|------------|
| 1 | Дом хранилища | `~/.mnemos/`, `mnemos.db` | `~/.vesma/`, `vesma.db` | Выполнить `vesma migrate-store` (раздел 2) |
| 2 | Канонический префикс тегов | в хранилище `mnemos:*`, алиас `vesma:*` | в хранилище `vesma:*`, `mnemos:*` принимается на входе | Теги перепишет мовер; ввод остаётся свободным (раздел 7) |
| 3 | Секция конфига | `mnemos:` | `vesma:` (оставленная секция `mnemos:` громко роняет загрузку) | Перепишет мовер; или переименовать вручную (раздел 4) |
| 4 | Переменные окружения | читались `MNEMOS_*` / `VESMARO_*` / `VESMA_*` | только `VESMA_*` | Переименовать экспорты; перегенерировать автодополнение (раздел 4) |
| 5 | Имена MCP-тулов | канон `mnemos_*`, `vesma_*` за бренд-флагом | только `vesma_*`; `mnemos_*` отвечает `Unknown tool` | Перезапустить `vesma integration setup`; обновить allowlist'ы (раздел 5) |
| 6 | Python-пакет | `import vesmaro` / `import mnemos` | только `import vesma` | Заменить импорты, переустановить (раздел 6) |
| 7 | Поле схемы экспорта | `mnemos_version` | `vesma_version` (импорт принимает оба) | Читать новый ключ; старые экспорты импортируются (раздел 6) |
| 8 | Маркер доверия | `mnemos:no-federate` | **Без изменений** — байт-стабилен по дизайну | Ничего; не переименовывать (раздел 7, FAQ 3) |

На каждую строку — одно действие: строки 1–3 закрывает мовер хранилища,
строки 4–7 — разовые правки на вашей стороне, строка 8 намеренно заморожена.

## 2. Пошаговое обновление хранилища

Мовер — явная команда оператора. Она **никогда** не запускается автоматически
ни при загрузке, ни при обновлении — вы вызываете её сами, на тихой машине,
по одному устройству за раз (остальные машины — по очереди, после того как
первая доказала полный прогон).

Контракт безопасности, который обеспечивает сама команда `vesma migrate-store`:

- **Только явные пути** — `--from` и `--to` обязательны; ничего не
  угадывается. Пропущенный `--from` печатает кандидатов и ничего не делает.
- **Dry-run — поведение по умолчанию** — без `--apply` команда только читает
  и печатает отчёт; исходное хранилище не меняется.
- **Снапшот до любых изменений** — на `--apply` снапшот через SQLite backup-API
  сохраняется в `<to>/../migrate-snapshot-<метка времени>/`, проверяется на
  читаемость и остаётся как артефакт отката.
- **Проверка покоя** — живой сокет сервиса или удерживаемая блокировка базы —
  громкий отказ, никакой миграции параллельно с живым писателем.
- **Никаких тихих развилок** — свежая установка без конфига отказывается
  создавать новый `~/.vesma`, пока живо старое хранилище `~/.mnemos`.
- **Приватность** — в отчёте только пути и счётчики, никогда значения записей.

### Шаг 0 — сначала обновите пакет

Мовер поставляется с 6.0. Обновите установку на линию 6.0 и подтвердите:

```bash
vesma update check
vesma update apply          # или: pip install --upgrade vesma / uv tool upgrade vesma
vesma --version             # ожидаем 6.0.x
```

### Шаг 1 — бэкап

Мовер на шаге 4 делает собственный проверенный снапшот, но свежий
пользовательский бэкап перед любой операцией с данными — дешёвая страховка:

```bash
vesma export -o vesma-backup-pre60.sqlite -f sqlite
```

Полные процедуры, включая восстановление на точку времени, живут в
[Backup & Restore](../admin/runbooks/backup-restore.md).

### Шаг 2 — остановите запущенный vesma service

Проверка покоя отказывается мигрировать живое хранилище. Остановите все пишущие
компоненты (встроенное ядро и, если установлены, сайдкары):

```bash
vesma service stop core
vesma service stop board     # если установлен
vesma service stop metrics   # если установлен
vesma service status         # подтвердите: всё остановлено
```

`vesma service stop` идемпотентен — уже остановленный компонент сообщается
как есть, это не ошибка. Если вы запускаете `vesma serve` или
`vesma mcp-server` вручную, без сервиса, остановите и эти процессы.

### Шаг 3 — dry-run (поведение по умолчанию)

```bash
vesma migrate-store --from ~/.mnemos --to ~/.vesma
```

Оба пути обязательны. Цель **не должна существовать вообще** — даже как
пустой каталог; мовер создаёт её сам. Ожидаемый вывод (числа иллюстративные;
у вас будут свои):

```text
migrate-store — mode: dry-run
  from: /home/user/.mnemos
  to:   /home/user/.vesma
  snapshot (on --apply): /home/user/migrate-snapshot-20261007-…

  Records
    total:                 3790
    status=published:      3610
    project=mnemos:        3790

  Planned rewrites (exact prefixes only)
    mnemos:<subtype> -> vesma:<subtype>:  8120
    project:mnemos -> project:vesma:      3790
    duplicate tags removed:               0
    trust markers kept byte-stable:       14

  Files
    vault present: True
    config present: True
```

Прочитайте план: общее число записей, запланированные перезаписи тегов/слагов
и количество сохранённых маркеров. Ничего не записано — источник не тронут.

> Один раз можно намеренно опустить `--from`: `vesma migrate-store` напечатает
> найденные дома-кандидаты (`~/.mnemos`, `~/.local/share/vesma/core`,
> `~/.vesma`) и выйдет, ничего не трогая. Это контракт discovery — только
> подсказки, никогда автоматический выбор.

### Шаг 4 — применить

```bash
vesma migrate-store --from ~/.mnemos --to ~/.vesma --apply
```

Мовер снимает снапшот источника, материализует новое хранилище **из
снапшота** в staging-каталоге, переписывает там теги и слаги, проверяет и
публикует результат в `--to` атомарным переименованием. Старый дом остаётся
байт-в-байт на месте — не переименовывается и не удаляется. Ожидаемый отчёт:

```text
migrate-store: applied and verified
  target:   /home/user/.vesma
  snapshot: /home/user/migrate-snapshot-20261007-… (rollback artifact)
  records:  3790
  mnemos:<subtype> -> vesma:<subtype>:  8120
  project:mnemos -> project:vesma:      3790
  duplicate tags removed:               0
  trust markers kept byte-stable:       14

  Config
    source: /home/user/.mnemos/config.yaml
    section mnemos: -> vesma: renamed: True
    paths re-rooted: 3
    db_name pinned to vesma.db: True

  Verification
    record counts equal: True
    id-set digest equal: True
    sample field checksums: 10 checked, 0 mismatched
    FTS rebuilt + integrity ok: True
    sqlite quick_check: ok on all moved databases
```

**Проверьте отчёт, прежде чем идти дальше.** Число записей должно совпасть с
total из dry-run; каждая строка верификации должна читаться `True` / `ok` /
`0 mismatched`. Мовер отказывается сообщать успех на перекошенном хранилище —
но прочитайте числа сами. Добавьте `--json` к любому запуску, чтобы получить
машинночитаемый отчёт (только пути и числа).

После прогона — чек-лист миграционного окна (из ADR-0044, вручную по
дизайну): выполните recall известного чекпоинта и — если вы федерируете — сделайте
один pull против живого 5.x-пира.

### Шаг 5 — переключите установку на новый дом

Мовер записывает канонический `config.yaml` в новый дом (секция
переименована `mnemos:` → `vesma:`, пути перепривязаны, зафиксирован
`db_name: vesma.db`). В этом релизе встроенный путь конфига по умолчанию —
всё ещё старый, поэтому укажите установке новый конфиг явно:

```bash
export VESMA_CONFIG=~/.vesma/config.yaml    # зафиксируйте в env/юните сервиса
vesma service start core
vesma service health                        # ожидаем OK
vesma doctor                                # полная проверка установки
```

`vesma doctor` проверяет конфиг, базу, хранилище-vault, очередь, MCP,
интеграцию, автодополнение и контракт тегов — каждая проверка должна
отчитаться PASS. Здесь же перезапустите `vesma integration setup` — он
обновит сгенерированные файлы харнесов до написаний 6.0 (см. раздел 5).

### Коды выхода мовера

Каждый отказ — типизированный код выхода с однострочной причиной в stderr
(`migrate-store: …`). Стабильный контракт:

| Код | Значение | Что делать |
|-----|----------|------------|
| 0 | Успех (отчёт dry-run или применено и проверено) | Идти к следующему шагу |
| 2 | Ошибка использования — отсутствующий/некорректный `--from`/`--to` | Перезапустить с обоими явными путями |
| 3 | Discovery отказался — `--from` опущен | Кандидаты перечислены в сообщении; перезапустить с явным `--from` |
| 4 | Нарушение покоя — сервис жив / удерживается блокировка базы | `vesma service stop core` (остановить писателей), затем повторить |
| 5 | Снапшот не удался (ошибка создания/проверки/записи) | Ничего не мигрировано; проверить место и права; повторить |
| 6 | Верификация не прошла (пост-проверки) | Staging удалён, снапшот сохранён, источник не тронут; разобраться по отчёту и повторить — или восстановиться из снапшота и завести issue |
| 7 | Уже мигрировано — вежливый отказ | Цель — мигрированное хранилище; делать нечего |
| 8 | Некорректный источник — путь не 5.x-хранилище | Проверить `--from` (ожидается `mnemos.db` под `data/`) |
| 9 | Конфиг заблокирован — неизвестные ключи, ключи вне схемы или обе секции, `mnemos:` и `vesma:` | Исправить названные ключи в исходном конфиге руками, затем повторить |

Любой код кроме 0 на `--apply` означает: цель не опубликована. Снапшот
остаётся на месте, старый дом остаётся байт-идентичным.

## 3. Что мовер трогает — и чего не трогает никогда

Переписывается (только точные префиксы, всё остальное байт-в-байт):

- теги `mnemos:<subtype>` → `vesma:<subtype>` — в поле тегов, денормализованной
  колонке `project` и FTS-индексе (пересобирается);
- слаг основного проектного пространства `project:mnemos` → `project:vesma`;
- `data/mnemos.db` → `data/vesma.db`;
- конфиг: секция `mnemos:` → `vesma:`, значения типов `Path` со старого дома
  перепривязываются к новому, `db_name` пинится в `vesma.db`; неизвестные имена
  ключей роняют прогон с кодом 9, а не выбрасываются молча.

Не переписывается никогда:

- **содержимое записей** — заголовки, тексты, строки провенанса, где случайно
  встречаются старые слаги: сохраняются байт-в-байт;
- **векторы** — ключуются идентификаторами, не тронуты;
- **маркер доверия `mnemos:no-federate`** — остаётся байт-стабильным; в
  отчёте видно количество сохранённых маркеров (раздел 7);
- **старый дом `~/.mnemos/`** — остаётся как есть; удалять его — ваше
  решение, после того как новое хранилище подтверждено на реальной нагрузке.

## 4. Машинные конфиги и окружение

### Файл конфига (YAML)

Переименуйте секцию верхнего уровня; все ключи внутри сохраняют имена:

```yaml
# 5.6.x                      # 6.0
mnemos:                      vesma:
  data_dir: ~/.mnemos/data     data_dir: ~/.vesma/data
  vault_path: ~/.mnemos/vault  vault_path: ~/.vesma/vault
                               db_name: vesma.db
```

Конфиг, в котором осталась секция `mnemos:`, в 6.0 **не загружается** — с
громкой ошибкой валидации, никогда с тихим откатом к дефолтам. Если конфиг
сделал мовер (рекомендуется), это уже сделано и провалидировано против
реальных моделей настроек; при ручной правке переименуйте ключ секции и
подтвердите загрузку через `vesma doctor`.

### Переменные окружения

Единственный честный префикс — `VESMA_*`. Написания 5.x `VESMARO_*` и 4.x
`MNEMOS_*` больше не читаются — причём молча: устаревший экспорт тихо
проваливается в значение по умолчанию.

| 5.6.x | 6.0 |
|-------|-----|
| `VESMARO_API__HOST`, `VESMARO_EXPORT_PASSPHRASE`, … | `VESMA_API__HOST`, `VESMA_EXPORT_PASSPHRASE`, … |
| `VESMARO_FED_PEER_*_URL`, `VESMARO_SYNC_*` | `VESMA_FED_PEER_*_URL`, `VESMA_SYNC_*` |
| `MNEMOS_SYNC_*` (шим для sync-peers.sh) | `VESMA_SYNC_*` |
| `VESMARO_CONFIG` / `MNEMOS_CONFIG` | `VESMA_CONFIG` (без изменений, канон с 5.3) |
| `VESMARO_AUTO_COLLECT`, `VESMARO_UPDATES_CHECK`, `VESMARO_ORT_THREADS`, `VESMARO_OPENROUTER_API_KEY` | те же имена под `VESMA_` |

Правила на память:

- Вложенные настройки — `VESMA_<СЕКЦИЯ>__<ПОЛЕ>` (двойное подчёркивание).
  Вложенные переменные самой секции хранилища — `VESMA_VESMA__*`, например
  `VESMA_VESMA__DATA_DIR`; короткие алиасы `VESMA_DATA_DIR` и
  `VESMA_VAULT__VAULT_PATH` продолжают работать и читаются легче.
- После переименования перегенерируйте автодополнение оболочки — старые
  скрипты устанавливают устаревшую переменную `_VESMARO_COMPLETE`: `vesma completion`
  (оболочка определяется автоматически).
- Перезапустите `vesma integration setup`: сгенерированные env-блоки теперь
  пишут канонические имена.
- Обновите env-файлы для `sync-peers.sh` до написаний `VESMA_SYNC_*`.

Проверьте, что легаси не осталось: `vesma doctor` (он загружает реальный
конфиг так же, как это сделает сервер) и вручную
`env | grep -iE 'mnemos|vesmaro'` в окружении сервиса.

## 5. MCP-обвязка

MCP-сервер регистрирует **только** имена тулов `vesma_*`. Легаси-имена
`mnemos_*` выпилены: клиент с allowlist'ом на старые имена перестаёт видеть
все тулы, а прямой вызов `mnemos_*` отвечает `Unknown tool`. Бренд-переменная
окружения ушла вместе с ними — vesma-only поверхность безусловна.

1. Перезапустите развёртывание: `vesma integration setup` (идемпотентно —
   обновляет MCP-регистрации и обвязку агентов на месте).
2. Обновите конфиг харнеса: allowlist'ы тулов и любая автоматизация,
   вызывающая тула по имени, переезжают с `mnemos_*` на `vesma_*`.
3. Полный каталог — в [mcp-tools.md](mcp-tools.md): те же тула, те же входы,
   новый префикс.

## 6. Python и API-поверхности

Если вы интегрируетесь с Vesma как с библиотекой или разбираете её экспорты:

| 5.6.x | 6.0 |
|-------|-----|
| `import vesmaro` / `from vesmaro import …` | `import vesma` / `from vesma import …` |
| `import mnemos` (шим совместимости) | удалён — `ModuleNotFoundError` |
| `importlib.resources.files("vesmaro")` | `importlib.resources.files("vesma")` |
| `settings.mnemos.data_dir` | `settings.vesma.data_dir` |
| ключ экспортного JSON `mnemos_version` | `vesma_version` (импортёр принимает и старый ключ) |
| консольные скрипты `vesma` / `vesmaro` / `mnemos` | установлены все три; канон — `vesma`, алиасы указывают на ту же точку входа |

Периода устаревания у имён импорта нет — 6.0 это жёсткий срез. После
обновления переустановите пакет (`uv sync` / `pip install -e .`); wheel'ы
собираются только из `src/vesma`. Защищено и не менялось: организация
`github.com/vesmaro`, образ `ghcr.io/vesmaro/vesma`, npm-скоуп, строка
схемы `vesmaro.federation.v1` — это идентичности федерации/реестров,
а не имена импорта.

## 7. Теги

Канонический префикс хранения теперь `vesma:*` — новые и мигрированные
записи хранятся как `vesma:<subtype>`. Менять то, как вы печатаете, не
нужно: старое написание `mnemos:` принимается как входной алиас на каждой
поверхности (`--tags` в CLI, тег-фильтры HTTP API, MCP-вызовы) и
нормализуется к канону при записи. Неизвестные подтипы громко отвергаются
в любом написании. Полный контракт: [tag-contract.md](tag-contract.md).

Две границы, которые надо знать:

- **Не выполняйте перезапись тегов вручную через `vesma tags rename`.**
  Этот тул — для других префиксов; мовер — единственный путь, который
  переписывает пространство подтипов вместе с FTS-индексом, слагом проекта и
  конфигом — атомарно и с верификацией.
- **`mnemos:no-federate` остаётся ровно таким, как есть.** Маркер исключения
  из федерации сохраняет старое написание бессрочно — это маркер доверия,
  и его стабильность в смешанном парке 5.x/6.0 и есть смысл. Ввод
  `vesma:no-federate` принимается и нормализуется в тот же сохранённый тег.

## 9. Откат

У каждого слоя миграции есть дорога назад:

- **Данные.** Каталог снапшота `<to>/../migrate-snapshot-<метка времени>/` — артефакт
  отката, проверенный до любой записи. Старый дом `~/.mnemos/` мовер не
  модифицирует вовсе. Чтобы вернуться: снова направьте установку на старый
  дом (прежний `VESMA_CONFIG` / путь конфига) и запустите сервис — 5.x-хранилище
  цело.
- **Пакет.** Релизы 5.6.x остаются ставиться с PyPI:
  `vesma update apply --to 5.6.5` или явное указание версии
  (`pip install vesma==5.6.5` / `uv tool install vesma==5.6.5`). Откатывайте
  пакет вместе с правками конфига (верните написания `VESMA_*`/легаси,
  которых ждёт 5.6.x, — или просто старый конфиг-файл).
- **Порядок.** Пакет и хранилище откатываются парой: код 5.6.x не читает
  теги `vesma:*` и `vesma.db`, а код 6.0 читает оба написания — поэтому
  безопасное направление отката всегда «старый пакет + старый дом», и только
  потом что-либо удалять. Держите снапшот, пока новое хранилище не переживёт
  реальное рабочее окно.

## 10. FAQ

**Я ничего не потеряю?**
Мовер построен так, чтобы полусделанная миграция не могла выдать себя за
успешную: сначала снапшот, верификация до публикации; содержимое записей
сохраняется байт-в-байт (переписываются только префикс тегов, колонка проекта и
FTS-индекс); счётчики записей, дайджест множества идентификаторов и
контрольные суммы образцов должны совпасть между источником и целью, иначе
прогон отказывается сообщать успех. Старый дом остаётся нетронутым как
вторая независимая копия. Худший случай — неудавшийся прогон, а он оставляет
вас ровно там, где вы начали, плюс снапшот.

**Что с федерацией с 5.x-пирами?**
Она продолжает работать. 6.0 держит окно двойного приёма: записи с тегами
`mnemos:*`, приходящие от пиров, принимаются, сохраняются и лениво
переписываются в канон; отправляемые записи несут канонические теги. Окно
закрывается вместе с линией 5.x (EOL 2026-10-20); приём легаси-тегов
снимается не раньше 6.1. Мигрируйте машины по одной — смешанный парк и есть
то, для чего окно сделано.

**Почему маркер no-federate до сих пор называется `mnemos:`?**
По дизайну, и это не недосмотр, который можно потом зачистить по желанию.
Маркер — граница безопасности: он выгораживает записи с секретами из всех
экспортов и федеративных чтений. Переименование маркера доверия в парке,
где старое и новое написания сосуществуют, превращает границу в усилитель
эксфильтрации — запись с `vesma:no-federate` пройдёт мимо 5.x-пира, который
сопоставляет только старое написание. Поэтому маркер байт-стабилен, каждая
точка принуждения сопоставляет ровно это написание, а мовер отчитывается,
сколько маркеров сохранено. Его переименование, если оно когда-нибудь
случится, поедет атомарной волной код+данные — не миграцией хранилища.

**Почему миграция не запускается сама при обновлении?**
Намеренно. Перезапись данных — действие оператора с явной целью, снапшотом и
читаемым отчётом, а не побочный эффект загрузки. 6.0 нормально работает и с
немигрированным хранилищем — через входной алиас; тихое окно выбираете вы.

**Можно просто пересоздать хранилище и переимпортировать экспорт?**
Можно, но не нужно: мовер сохраняет чекпоинты, векторы и идентификаторы,
которые круг export/import не гарантирует полностью. Мовер и проще — одна
команда, один отчёт.
