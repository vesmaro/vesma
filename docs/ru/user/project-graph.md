# Граф проектов

**🌐 Language / Язык:** [English](../../en/user/project-graph.md) · Русский

> Vesma умеет знать вашу кодовую базу так же, как сессии: в виде searchable-карты
> символов. Проиндексируйте проект один раз — и агенты получают схемы файлов,
> поиск по символам, трассировку вызовов и сниппеты диапазонов строк — с
> отфильтрованными секретами и без единого байта исходника в хранилище.

---

## Что это такое

**Граф проектов** — это карта символов кодовой базы уровня памяти, построенная
парсингом tree-sitter'ом (ADR-0032). Она живёт в sidecar-файле SQLite,
`code_graph.db`, рядом с основным хранилищем в data dir (по умолчанию
`~/.mnemos/data/`).

Что хранится — и что не хранится никогда:

| Хранится | Не хранится никогда |
|----------|---------------------|
| Пути файлов (repo-relative), языки, диапазоны строк | Содержимое файлов, байты исходника (PG1) |
| Имена и квалифицированные имена символов | Докстроки, комментарии, строковые литералы |
| Формы сигнатур (без значений по умолчанию) | Тела кода |
| Рёбра между символами, хэши содержимого | Секреты — они «травят» файл (см. ниже) |

Поскольку в графе нет байтов исходника, это *производные данные*: удалите —
и их всегда можно перестроить из источников. Sidecar не нуждается в бэкапах —
`code_graph.db` одноразовый по дизайну.

Узлы и рёбра:

| Вид | Примеры |
|-----|---------|
| **Узлы** | `Project`, `File`, `Module`, `Class`, `Function`, `Method`, `Type` — плюс `Command` / `Route` на определяющем репо (схема v2, [ниже](#cli-команды-и-rest-роуты-в-графе-схема-v2)) |
| **Рёбра** | `CONTAINS_FILE`, `DEFINES`, `IMPORTS`, `CALLS`, `INHERITS`, `TESTS`, `USES` — плюс `INVOKES` / `HANDLES` (схема v2) |

Ребро `USES` — маркер честности всего семейства: вызов записывается как
`CALLS`, только если парсер доказал цель; всё остальное, похожее на вызов,
получает `USES` с `provenance: heuristic`. Ребро из графа никогда не
претендует на большую уверенность, чем имеет.

## Поддерживаемые языки

| Язык | Начиная с | Поверхность индексации |
|------|-----------|------------------------|
| Python | PG-0 (#438) | `.py` |
| Go (#470) | 2026-10 | `.go` |

Всё остальное просто не индексируется — неизвестное расширение никогда не
проваливается в чужой парсер. Что граф видит в Go-дереве:

- **Символы** — функции верхнего уровня (`Function`), методы с приёмником
  (`Method`, qname `pkg.Type.Name`), типы struct/interface (`Class`),
  прочие именованные типы и алиасы (`Type`). Квалифицированные имена несут
  префикс каталога пакета (`pkg.util.Greeter.Greet`); qname узла-модуля —
  это каталог пакета.
- **Доказанные `CALLS`** — вызовы по простому идентификатору внутри одного
  Go-пакета (область видимости пакета делает имя уникальным, в том числе
  между файлами пакета) и вызовы `pkg.Ident(...)` через разрешённый импорт.
  Приведение типа (`Base(x)`) считается вызовом типа — зеркально
  питоновскому правилу конструктора.
- **Эвристические `USES`** — вызовы методов на значениях/указателях
  (`obj.Method(...)`; тип приёмника не выводится, поэтому совпадение по
  имени остаётся эвристикой) и ссылки на типы из composite-литералов
  (`&Server{...}`) и аргументов типов у `new`/`make`.
- **`INHERITS`** — встраивание struct/interface; **`IMPORTS`** — когда путь
  импорта совпадает с каталогом пакета в репозитории (ребро указывает на
  модуль первого по сортировке файла пакета; пути stdlib/внешних пакетов
  не разрешаются ни во что); **`TESTS`** — от `foo_test.go` к модулю своего
  пакета.
- **Честно пропускается** — удовлетворение интерфейсов (в Go неявное; ребро
  не выдумывается), вызовы через переменные-функции, инстанциации дженериков
  (`F[T](...)`), dot- и blank-импорты. Строка пути импорта — единственное
  строковое содержимое, которое вообще читается, и только для разрешения
  импортов — в стор она не попадает (PG1 держится для Go-источников так же,
  как для Python).

## CLI-команды и REST-роуты в графе (схема v2)

Собственная поверхность движка — первоклассные данные графа. Когда
индексируемый корень — **это checkout vesma** (определяется по наличию
маркеров пакетов `cli` / `api` движка внутри корня, никогда по
захардкоженному пути), surface node-source extension добавляет на каждом
полном индексе ещё два вида узлов:

| Вид | Один узел — это | Пример |
|-----|-----------------|--------|
| `Command` | один путь вызова CLI: полное имя команды, однострочный help, число опций, до 16 компактных пар «параметр → help» | `vesma graph delete` |
| `Route` | один HTTP-метод + путь: однострочное описание и имя функции-обработчика | `GET /api/v1/metrics` |

Данные берутся из ЖИВЫХ реестров движка — то же typer/click-дерево, по
которому ходит shell-completion движок (`vesma __complete`), и
`app.routes` FastAPI (все подключённые роутеры: sessions, auth,
federation) — второго парсера, который мог бы разъехаться, нет. Каждый
узел связывается со своей функцией-обработчиком ребром **`INVOKES`**
(Command → handler) или **`HANDLES`** (Route → endpoint), когда обработчик
разрешается в индексируемом дереве (сначала точное совпадение пути
импорта, затем уникальное совпадение по точечному суффиксу для
src-layout; неразрешённый обработчик ребра НЕ получает — то же правило
честности, что у неразрешённых импортов).

Токен-экономика (смысл этой механики): «как удалить индекс графа» — это
ОДИН ограниченный поиск вместо ~18.7k-токенного discovery через
`--help`:

```
vesma_search_graph(project_id="vesma", query="graph delete", kind="Command")
→ 1 строка: "vesma graph delete" · help: "Delete a project's graph index…"
  options: 5 · params: {project, --force, --confirm-name, --agent, --reason}
```

Ограждения:

- help-строки — ТОЛЬКО первая строка: полный текст help никогда не едет в
  узле;
- каждая выдаваемая строка проходит детектор секретов (попадание снимает
  строку, но не узел);
- корень без маркеров — любой чужой репозиторий — не получает НИ ОДНОГО
  surface-узла: extension регистрируется хостом один раз, а решение
  принимается по каждому корню;
- `vesma_project_graph_status` показывает разбивку `node_kinds` по видам —
  вклад extension виден, а не предполагается.

**Агентам из других проектов:** команды и роуты — это код ОПРЕДЕЛЯЮЩЕГО
репозитория. Агент, работающий в другом проекте, запрашивает их с
`project_id` проекта самого репо vesma (того, чей зарегистрированный
корень несёт движок), а не своего проекта — и идёт по ребру
`INVOKES`/`HANDLES` в код обработчика.

**Существующие индексы:** surface-узлы появляются при следующем ПОЛНОМ
(пере)индексе — инкрементальный классификатор перестраивает весь проект
при любом изменении файла, достаточно `touch` любого отслеживаемого
файла; либо удалите индекс (`vesma_delete_graph_project`) и
проиндексируйте заново.

## Включите граф для проекта

Граф индексирует **только зарегистрированные корни** (PG2). Корень — это
первый абсолютный путь в записи проекта (`paths[0]`). Регистрация — шаг
оператора: проекты, автосозданные записью памяти, не имеют путей, так что
вызовы графа для них отвечают отказом конфайнмента (текст отказа называет
способ исправить), пока корень не зарегистрирован. Два способа:

- **Со стороны агента** (#454): инструмент `vesma_register_project` —
  `project_id`, абсолютный `root` и обязательная атрибуция `agent`. Корень
  должен существовать, нести packaging-манифест или `.git` и не быть
  `$HOME`/корнем файловой системы (сравнение на realpath, так что symlink-
  или `..`-написание запрещённой цели тоже отказывается, #464).
  Идемпотентен при уже зарегистрированном корне.
- **CLI**: `vesma graph register <project> <root>` — те же ограды и
  аудит-трейл (`manual-register`), из терминала.

> **Граница threat-модели (issue #464).** Регистрация — это **read-scope
> грант**: как только корень зарегистрирован, его символы и сниппеты
> читаются через граф-инструменты любым агентом на сервере — значит,
> разрешение агенту регистрировать произвольные корни расширяет его
> собственную read-область на любой git-checkout хоста. Агентский путь
> поэтому ограждён флагом `code_graph.agent_registration` (по умолчанию
> `true` из single-user stdio-допущения; на multi-agent или
> untrusted-agent деплойментах ставьте `false` — ограждённая попытка
> отказывается и аудируется `manual-register-refused`). Операторский CLI-
> путь не ограждается никогда. Отказы регистрации и repoint —
> аудируемые события первого класса (`manual-register-refused` /
> `repoint-refused`), а `vesma graph repoint` чинит **призраки** —
> регистрацию, чей корень ещё существует на диске, команда отказывается
> (перенос корня — не repoint).

Прямая запись в стор (то, что делают инструменты под капотом) тоже работает:

```python
from vesma.models import Project
mgr.sqlite.save_project(Project(name="vesma", paths=["/home/you/vesma"]))
```

Явная регистрация **не считается** против `auto_register_max_projects` —
тот потолок ограничивает только авто-путь.

Дальше поток — три вызова инструментов (каждый требует `agent` — см.
[Границы и FAQ](#границы-и-faq)):

1. **Индексация** — `vesma_index_project` с `project_id` и `agent`. Первый
   запуск — полная индексация; последующие — инкрементальные по умолчанию
   (пропуск, когда ничего не изменилось, по классификации mtime+size).
2. **Проверка** — `vesma_project_graph_status`: объёмы узлов/рёбер/файлов,
   процент fresh, ошибки разбора и число poisoned-файлов.
3. **Использование** — `vesma_search_graph` для ранжированного поиска по
   символам, `vesma_get_file_outline` для схемы файла, `vesma_trace_path`
   для обходов вызовов/навигации, `vesma_get_code_snippet` для диапазонов
   строк.

Хотите без касаний? Следующая секция — про нативный авто-путь; ручной поток
выше в любом случае сохраняет свой полный контракт.

## Гибридный поиск: literal-фолбэк (W-H)

Символьный индекс — это только формы: строковые литералы (имена
инструментов, пути роутов, имена env-переменных) для него невидимы. С
волны W-H `vesma_search_graph` — **гибридный**: когда символьный граф не
нашёл ни одного совпадения, ограниченный read-only скан
зарегистрированного корня проекта отвечает строками контента вместо пустого
результата.

Поведение:

- **Сначала символы, всегда.** Есть символьное совпадение — ответ состоит
  только из символьных строк, фолбэк не запускается. Каждая символьная
  строка теперь несёт добавочное поле `match_kind: "symbol"`.
- **Literal-строки.** На пустом символьном результате скан отвечает
  строками `match_kind: "literal"` (`path` / `line` / `snippet`,
  repo-relative, текст строки обрезан по краям и ограничен 240 символами,
  максимум 20 строк). Узловых id у них нет — это содержимое файлов, а не
  узлы графа. Маркер верхнего уровня `fallback_used: true` появляется
  ТОЛЬКО когда фолбэк запускался (иначе отсутствует — форма без null-
  заглушек). `total_matches` считает весь ответ: когда отвечает фолбэк,
  он равен числу выданных literal-строк (непустой фолбэк никогда не
  показывается как 0).
- **Ограниченный.** Скан переиспользует denylist поверхности индексатора
  (`.git`, `.venv`, `node_modules`, vendored-деревья, dotfiles и файлы с
  «секретными» расширениями никогда не открываются), не ходит по симлинкам,
  пропускает бинарный контент и файлы больше 1 МиБ и останавливается по
  жёстким лимитам (число файлов, ~2 с по часам). Скан, упёршийся в лимит,
  логируется как неполный.
- **В границах корня.** Скан никогда не покидает зарегистрированный корень.
  Незарегистрированный проект отказывается до всякого скана.
- **PG4 держит.** Каждая literal-строка проходит тот же детектор секретов,
  что и выдача сниппетов; находка УНИЧТОЖАЕТ строку (сырой контент никогда
  не выдаётся), а poisoned-пути (PG3) не выдают контент вовсе. Скан, который
  не может завершиться безопасно, вырождается в честную пустоту без
  фолбэка — никогда в сырой контент.
- **Ручка.** `code_graph.literal_fallback` (по умолчанию `true`) выключает
  ногу; `search_graph` остаётся символьным. REST-близнец
  `POST /graph/search` наследует поведение целиком без изменений.

## Секция walk: аренда окрестности (PG-1, ADR-0038)

Структурный вопрос — «кто вызывает `X`, один-два хопа» — раньше стоил либо
вызова `vesma_trace_path` на каждый символ, либо чтения файлов целиком.
Когда `code_graph.search_walk` включён, каждый `vesma_search_graph` с
символьными совпадениями СЛЕДУЕТ дополнительно обходить окрестность хитов и
отвечать ОТДЕЛЬНОЙ секцией `walk`:

```json
"walk": {
  "origins": ["Base", "Base.greet", "make_base"],
  "k": 3,
  "nodes": [ { "id": "...", "qname": "Base", "kind": "Class", "path": "pkg/helper.py",
               "start_line": 1, "end_line": 3, "depth": 0 }, "…"],
  "edges": [ { "from": "...", "to": "...", "kind": "CALLS", "provenance": "tree-sitter" } ],
  "truncated": false,
  "epoch": 4,
  "walk_cursor": 0,
  "has_more": false,
  "last_indexed_at": "2026-10-06T00:00:00+00:00"
}
```

Как это работает:

- **Отдельно, никогда не подмешивается.** Walk — своя секция верхнего
  уровня; `results` сохраняют пиновую форму поиска без изменений. Секция
  присутствует ТОЛЬКО когда сработала (символьные хиты существовали) —
  иначе отсутствует, никогда null/пустой скелет (прецедент формы
  `fallback_used`). Literal-фолбэк нога никогда не ходит (у его строк нет
  узловых id).
- **Origins = квота.** `k = min(ceil(limit/5), limit//2)` топовых
  ранжированных символьных хитов становятся origins хода (чистая функция
  от `limit`).
- **Два хопа, оба направления.** Узлы — PG1-строки метаданных
  (`id`/`qname`/`kind`/`path`/`start_line`/`end_line`/`depth`) — без
  сигнатур, пути repo-relative, сортировка `(depth, qname)`. Рёбра хранят
  трейс-контракт (`from`/`to`/`kind`/`provenance`), ход идёт in+out от
  каждого origin, глубина ≤ 2, по структурным видам
  `CALLS` / `IMPORTS` / `INHERITS` / `USES` / `INVOKES` / `HANDLES`
  (файловые рёбра — `CONTAINS_FILE` / `DEFINES` / `TESTS` — не участвуют).
- **Ограничено и честно.** На каждый origin общий ходитель держит кап
  fanout (32) и кап total work (512 посещённых узлов) НЕЗАВИСИМО от `k` +
  границу проекта (ребро, выходящее из проекта, пропускается, не
  проходится); любой кап или граница ставит `truncated: true` — ход
  никогда не притворяется, что показал всё.
- **Свежесть в нагрузке.** Секция несёт `epoch` графа — консюмеры
  инвалидируются по нему; TTL-кэша ходов нет.
- **Свой бюджет.** Строки `nodes` хода идут под тем же токен-контрактом
  (потолок 4 байта/токен, порезка целыми строками) со СВОИМ `walk_cursor`
  — paginate секцию через `walk_cursor` так же, как `results` через
  `cursor`.
- **Сам ценируется.** Каждое исполнение хода пишет строку `search-walk` в
  sidecar `graph_audit` с `out_tokens` (стоимость ответа) и
  `avoided_bytes` (байты файлов-источников посещённых узлов, которые агент
  иначе открыл бы целиком).
- **Ручка.** `code_graph.search_walk` (по умолчанию `false`) — период с
  выключенным флагом даёт измеряемую базовую линию «поиск + чтение»; ход
  включается осознанно (env: `VESMA_CODE_GRAPH__SEARCH_WALK`).

## Нативная авто-индексация (zero-touch)

С волны PG-0.5 граф индексируется **сам**: каждый вызов MCP-инструмента и
каждый хук `pre_llm_call` порождает фоновый *hint*, а hint может
авторегистрировать и проиндексировать проект — без вызова
`vesma_index_project`, без инструкций, без скиллов. Авто-работа идёт через
ту же сериализацию, лимиты PG7 и аудит-трейл, что и ручные запуски;
отличаются только `reason` в аудите (`auto-first` / `auto-stale`) и актор
(агент, пославший hint).

Как проходит первый контакт:

1. Агент — с указанным `agent`; **нет агента — нет авто-действия** (PG7) —
   вызывает любой MCP-инструмент внутри каталога проекта. Диспетчер
   порождает один hint: слаг проекта + текущий рабочий каталог. Hint никогда
   не блокирует и не ломает вызывающего; работа идёт в фоновом потоке
   планировщика.
2. Если проект **ещё не зарегистрирован**, авто-путь ищет в cwd
   packaging-**манифест**: `pyproject.toml`, `setup.py`, `package.json`,
   `go.mod` или `Cargo.toml` (локфайлы не считаются). Нет манифеста — нет
   авторегистрации: голый checkout с одним `.git` маркером намеренно не
   является, а `$HOME` и корень файловой системы отказываются даже при
   лежащем там манифесте.
3. Манифест есть → проект авторегистрируется по своему разрешённому корню и
   запускается первый индекс (`auto-first`). С этого момента строка-маячок
   появляется в выводе `assemble_context` сама.
4. Уже зарегистрирован и устарел → hint становится инкрементальной
   переиндексацией (`auto-stale`) с троттлингом по проекту (см. ниже).

Ограды именно авто-пути:

| Ограда | Что вы видите |
|--------|---------------|
| **Один корень = один граф** | Прежде что-то регистрировать, авто-путь ищет существующий проект с тем же разрешённым корнем и переиспользует его (аудит `auto-register-reused`) — никогда дублирующей строки проекта, никогда второго полного индекса. |
| **Потолок регистраций** | `auto_register_max_projects` (64) ограничивает, сколько проектов авто-путь вообще может создать; после потолка хинты молча пропускаются с аудитом `auto-register-capped` — никогда ошибкой вызывающему. |
| **Троттлинг** | `auto_reindex_min_interval_sec` (300 с) разделяет последовательные авто-действия по проекту. Штамп пишется *до* действия (reserve-then-act): неудачный авто-индекс не перезапускается каждым следующим хинтом. |
| **Приостановка** | Неудачный *первый* авто-индекс приостанавливает авто-путь для проекта: дальнейшие хинты пропускают его целиком — пока успешный ручной `vesma_index_project` (watch-опрос ездит тем же методом) или `vesma_delete_graph_project` не снимет флаг. Неудачная *stale*-переиндексация ничего не приостанавливает. |

Границы v1: вызов без `agent` авто-путь не запускает никогда; REST —
намеренно не hint-поверхность; регистрация с несколькими путями по-прежнему
индексирует только `paths[0]`. Выключить один авто-путь можно флагом
`code_graph.auto_index: false` — ручные инструменты продолжают работать.

## Поддерживайте свежесть: watch-опрос

`vesma_watch_start` регистрирует проиндексированный проект во
внутрипроцессном потоке опроса (без демона). На адаптивном интервале — база
5 с, +1 с за каждые 500 проиндексированных файлов, потолок 60 с — он
классифицирует файлы по mtime+size и переиндексирует только при фактических
изменениях, с аудитом под причиной `watch`.

- Регистрации живут в пределах процесса; перезапуск их сбрасывает.
- Глобальный потолок: 8 активных регистраций
  (`code_graph.watch_max_registrations`).
- `vesma_watch_status` показывает все регистрации и исход последнего опроса;
  `vesma_watch_stop` останавливает одну или все (идемпотентно).

## Перенесённые корни: «призраки» и `vesma graph repoint` (#450)

Каталог проекта, переименованный или перенесённый на диске, оставляет
**призрак**: авто-путь молча ничего не делает, `vesma_index_project`
отвечает отказом конфайнмента («registered root is missing on disk»), а до
#450 единственным выходом было удаление графа. Призраки видны:
`vesma_list_graph_projects` помечает их `root_missing: true`.

Починка — одна команда оператора:

```bash
vesma graph repoint <project> <new-root>
```

Ограды (громкие отказы, аудит с действием `repoint`, причиной
`graph-repoint`):

- новый корень должен существовать, быть абсолютным, нести
  packaging-манифест или `.git` (нельзя направить граф на посторонний
  каталог) и не быть `$HOME`/корнем файловой системы;
- один корень = один граф: новый корень, уже занятый другим проектом,
  отказывается;
- устаревший индекс **сносится** (он описывает старое дерево — производные,
  пересобираемые данные), приостановка авто-пути снимается, следующий
  запуск индексации собирает граф заново.

Призрак можно и удалить совсем — `vesma_delete_graph_project` (или
`vesma graph delete <project>` в CLI) сносит индекс, а за evidence-гейтом
(`confirm=true` + `confirm_name`, эхо имени проекта; в CLI `--force
--confirm-name <project>`) и саму строку регистрации. Попытка без гейта
отказывается и аудируется (`delete-refused`). «Живая» регистрация (корень
существует на диске) строку сохраняет — удаляется только производный индекс.

## Инструменты графа

| Инструмент | Что делает |
|------------|------------|
| `vesma_index_project` | Полная или инкрементальная индексация зарегистрированного корня; сериализуется по проекту |
| `vesma_project_graph_status` | Объёмы, свежесть, ошибки разбора, число poisoned-файлов по проекту |
| `vesma_search_graph` | Ранжированный поиск по имени / квалифицированному имени / пути; сигнатуры — opt-in; гибридный literal-фолбэк на пустом результате (W-H) |
| `vesma_trace_path` | BFS по рёбрам от одного символа (глубина ≤ 2, честный флаг `truncated`); неоднозначный голый хвост отвечает списком кандидатов (W-H) |
| `vesma_get_file_outline` | Схема символов одного файла — формы, никогда тела |
| `vesma_get_code_snippet` | Диапазон строк читается **с диска**, с проверкой свежести и сканом на секреты |
| `vesma_check_graph_coverage` | Вердикт по пути: `indexed` / `stale` / `parse-error` / `unindexed` / `poisoned` |
| `vesma_get_graph_schema` | Карта контракта: виды, лимиты, токен-контракт |
| `vesma_list_graph_projects` | Зарегистрированные проекты вместе со статусом индекса; призраки помечены `root_missing` |
| `vesma_delete_graph_project` | Удалить индекс (только sidecar); единственный способ очистить poisoned-набор |
| `vesma_register_project` | Зарегистрировать корень (#454) — ответ агента на «not registered» |

Плюс watch-семейство: `vesma_watch_start` / `vesma_watch_stop` /
`vesma_watch_status`.

Каждый оконный инструмент принимает `max_output_tokens` (128–1 000 000,
по умолчанию 3200) под детерминированным токен-контрактом: строки
отбрасываются целиком, никогда не режутся, курсор строго сдвигается вперёд. Полные
входные схемы и примеры: [mcp-tools.md, «Инструменты графа
проектов»](mcp-tools.md#инструменты-графа-проектов-adr-0032).

## Граф в ежедневной работе

Граф окупается только когда это ПЕРВАЯ остановка, а не последнее средство.
Рабочий цикл:

1. **Найти символ** — `vesma_search_graph` по имени / квалифицированному
   имени / пути. Ранжированные попадания, сигнатуры — по запросу; уже,
   чем шум grep'а.
2. **Провести по вызовам** — `vesma_trace_path` от найденного
   квалифицированного имени. Обход рёбер (вызовы / импорты / наследование)
   — тот ответ, который текстовый поиск не даёт структурно.
3. **Читать ровно нужное** — `vesma_get_file_outline` перед открытием
   большого файла, `vesma_get_code_snippet` для выбранных диапазонов
   строк.

**Когда побеждает grep.** Граф индексирует только символы (ноль байтов
исходника, PG1) — строковые литералы он не видит. Имена инструментов,
имена env-переменных, строки логов, комментарии и проза примеров в docs
остаются территорией grep'а. (Исключение — CLI-команды и REST-роуты
самого движка: это первоклассные узлы `Command`/`Route` на определяющем
репо, схема v2.) У незарегистрированного
репозитория графа нет вовсе — сначала загляните в
`vesma_list_graph_projects`. И «не проиндексировано» ≠ «не существует»:
`vesma_check_graph_coverage` различает `indexed` / `stale` / `unindexed`
/ `poisoned` прежде, чем вы решите, что символа нет.

**Гигиена.** `vesma_project_graph_status` / `vesma_check_graph_coverage`
— ворота честности: ошибки разбора остаются видимыми («чисто ≠ доказано»),
а poisoned-счётчик, целиком составленный из тестовых фикстур, — вопрос
allowlist'а, а не страха: ответ status прямо это подсказывает (`hints`),
а `secret_allowlist` ниже — лазейка.

## Безопасность и ограждения

Модель безопасности — ADR-0032 §6 (инварианты PG1–PG7); вот что она значит
для вас:

| Ограда | Что вы видите |
|--------|---------------|
| **Конфайнмент (PG2)** | Касаются только корней, зарегистрированных оператором. Произвольные пути, symlink-побеги и обход через `..` отклоняются. |
| **Poisoned-файлы (PG3)** | Файл, сработавший в детектор секретов при индексации, отравлен **навсегда**: символы остаются в графе, сниппеты не выдаются никогда. Два выхода: `vesma_delete_graph_project` и `secret_allowlist` оператора (ниже) — allowlist-путь пропускает отравление при индексации, а ранее отравленный allowlist-путь снимается с отравления при следующем индекс-запуске с аудит-строкой `allowlist-unpoison` (никогда не молча). Скан по диапазону при выдаче (PG4) allowlist'ом не отменяется. |
| **Скан при выдаче (PG4)** | Сниппеты читаются с диска в момент запроса — кэша сниппетов нет. Расхождение mtime+size+sha256 даёт маркер `stale`, но не содержимое; секрет в запрошенном диапазоне отклоняет весь диапазон, fail-closed. |
| **Fail-closed лимиты (PG7)** | 20 000 файлов / 500 МБ на проект. Превышение отклоняет ВЕСЬ индекс — частичный граф не публикуется никогда. |
| **Export-blind (PG5)** | Карта кода не покидает сервер: export-бандлы и payload'ы federation/mesh никогда не несут артефактов графа. Пиры индексируют собственные локальные источники. |
| **Атрибуция и аудит (PG7)** | Каждый вызов — чтение или запись — аудируется по агенту; вызовы без `agent` отклоняются с `attribution-required`. |
| **Ноль байтов исходника (PG1)** | Откройте sidecar — там имена, пути, диапазоны строк; ни кода, ни литералов, ни секретов в покое. |

## Исключаемые каталоги (эфемерные поверхности)

Индексатор никогда не заходит в эфемерные каталоги — деревья зависимостей,
сборочный вывод и git-worktree, размещённые ВНУТРИ зарегистрированного
корня. Живой случай (дефект 2026-10-03): worktree `wt/` внутри корня
проекта индексировался как собственные исходники — число файлов удвоилось
(376→746), а секрет-фикстуры внутри копии worktree отравлялись заново при
каждом индекс-запуске.

Работают два слоя, и первый выключить нельзя:

- **Встроенный denylist** (проверяется на любой глубине вложенности):
  `.git`, `.hg`, `.svn`, `.tox`, `.mypy_cache`, `.pytest_cache`,
  `.ruff_cache`, `__pycache__`, `venv`, `.venv`, `node_modules`, `dist`,
  `build`, `target`, `site-packages`, `wt` (конвенция
  `git worktree add wt/<name>`), плюс вендорные деревья (`vendor`,
  `vendored`, `third_party`, `3rdparty`).
- **Кноб `exclude_globs`** (`code_graph.exclude_globs`, по умолчанию —
  эфемерный список выше): режет каталоги ПОВЕРХ denylist. Голое имя
  (`wt`) матчит каталог с таким именем на любой глубине; элемент со
  слэшем матчит путь каталога относительно корня (семантика
  `fnmatch`). Задание поля ЗАМЕНЯЕТ список по умолчанию — но поднять
  встроенный denylist оно не может.

```yaml
code_graph:
  exclude_globs:
    - "wt"
    - "gen/**"   # глоб со слэшем матчит путь каталога от корня
```

Переопределение через окружение: `VESMA_CODE_GRAPH__EXCLUDE_GLOBS`
(JSON-массив, например `VESMA_CODE_GRAPH__EXCLUDE_GLOBS='["wt", "gen/**"]'`).

Тем же исключением руководствуются literal-фолбэк-скан и маяк свежести —
worktree, появившийся в корне после индексации, никогда не читается как
«устаревшие файлы» и не запускает авто-переиндексацию.

## Конфигурация

Все флаги живут под `code_graph:` в `config.yaml` (см. `config.example.yaml`).
Поверхность **включена по умолчанию** (решение владельца 2026-09-28).

| Ключ (`code_graph.`) | По умолчанию | Значение |
|----------------------|--------------|----------|
| `enabled` | `true` | Мастер-флаг 10 инструментов + REST-namespace `/graph/`; `false` скрывает всю поверхность (каждый вызов отвечает `code: "disabled"`). |
| `beacon` | `true` | Одна строка-хвост в выводе `assemble_context` со свежестью графа («indexed …, N/M files fresh — call vesma_search_graph»). Только при `enabled`. |
| `literal_fallback` | `true` | Гибридный поиск (W-H): когда символьный поиск не нашёл НИЧЕГО, ограниченный read-only скан зарегистрированного корня отвечает строками `match_kind: "literal"` (path/line/snippet) с маркером `fallback_used: true` — каждая строка проходит PG4-редакцию, poisoned-пути не выдают ничего, лимиты скана: число файлов / 1 МиБ на файл / ~2 с. `false` оставляет `search_graph` символьным. Env: `VESMA_CODE_GRAPH__LITERAL_FALLBACK`. |
| `search_walk` | `false` | Отдельная секция `walk` в `search_graph` (PG-1 M2, ADR-0038): при символьных хитах двухуровневый обход окрестности (in+out, глубина ≤ 2, квота `k = min(ceil(limit/5), limit//2)` origins, капы fanout 32 / total work 512 независимо от `k`) отвечает PG1-строками метаданных в своей токен-секции со своим `walk_cursor`, с `epoch` графа в нагрузке и самопрайсированной audit-строкой `search-walk` (`out_tokens` / `avoided_bytes`). Никогда не подмешивается в `results`; absent-when-empty; при выключенном флаге ответ байт-идентичен до-walk форме. Env: `VESMA_CODE_GRAPH__SEARCH_WALK`. |
| `auto_index` | `true` | Нативная авто-индексация (PG-0.5): MCP-вызовы и хинты `pre_llm_call` авторегистрируют (по манифесту) и индексируют проекты в фоне. `false` оставляет ручные инструменты. |
| `auto_register_max_projects` | `64` | Глобальный потолок авторегистраций; после него хинты молча пропускаются с аудитом `auto-register-capped`. |
| `auto_reindex_min_interval_sec` | `300.0` | Минимум секунд между фоновыми авто-(пере)индексациями по проекту. |
| `watch` | `true` | Взводит watch-опрос (`vesma_watch_start`); инертен до явной регистрации. |
| `index_max_files` | `20000` | Жёсткий лимит проиндексированных файлов на проект (fail-closed). |
| `index_max_source_mb` | `500` | Жёсткий лимит суммарных байтов исходника на проект, МиБ (fail-closed). |
| `secret_allowlist` | `[]` | Глобы путей относительно корня репозитория (`fnmatch`), чьи файлы пропускают отравление PG3 при индексации — выход для заведомо фейковых секрет-фикстур (тестовые данные, примеры в docs). Файл индексируется как обычно; ранее отравленный allowlist-путь снимается с отравления при следующем индекс-запуске (аудит `allowlist-unpoison`). Скан при выдаче (PG4) не отменяется. Удаление гло́ба не ретроактивно: снятый с отравления файл остаётся читаемым, пока его содержимое не изменится и снова не сработает детектор при индексации. Семантика `fnmatch`: `*` матчит и `/` (то есть `tests/*` достаёт и вложенные пути). |
| `exclude_globs` | `["wt", ".venv", "venv", "node_modules", "dist", "build", ".tox", ".git"]` | Глобы каталогов, исключаемых из поверхности индексации ПОВЕРХ встроенного denylist (см. «Исключаемые каталоги» выше). Голое имя матчит каталог на любой глубине; элемент со слэшем — путь каталога от корня репозитория (`fnmatch`). Задание поля заменяет список по умолчанию, но не поднимает встроенный denylist (`wt`, `node_modules`, `.git` и др. не индексируются никогда). Env: `VESMA_CODE_GRAPH__EXCLUDE_GLOBS` (JSON-массив). |
| `watch_max_registrations` | `8` | Глобальный потолок активных watch-регистраций на процесс. |
| `watch_base_interval_sec` / `watch_interval_per_500_files` / `watch_max_interval_sec` | `5.0` / `1.0` / `60.0` | Адаптивный интервал опроса: база + 1 с за каждые 500 файлов, с потолком. |

Продуктовый дефолт — `[]`: PG3 — охранный шлюз, а не неудобство.
Каноничный паттерн фикстур (фейковые секреты в тестовых данных; применён
на практике 2026-10-03) ограничивает лазейку тестовыми и
benchmark-деревьями, никогда — исходниками:

```yaml
code_graph:
  secret_allowlist:
    - "tests/**"
    - "benchmarks/**"
```

Переопределение через окружение — по каноническому шаблону настроек:
`VESMA_CODE_GRAPH__INDEX_MAX_FILES`,
`VESMA_CODE_GRAPH__INDEX_MAX_SOURCE_MB`,
`VESMA_CODE_GRAPH__SECRET_ALLOWLIST` (JSON-массив, например
`VESMA_CODE_GRAPH__SECRET_ALLOWLIST='["tests/fixtures/**"]'`).

## Границы и FAQ

- **Почему каждый вызов требует `agent`?** Атрибуция PG7: аудит-трейлы и
  ответственность по агентам. `vesma_recall_context` не несёт `agent`, так
  что поверхность графа никогда не ездит на нём — передавайте идентификатор
  вызывающего явно.
- **Мой проект — голый checkout с `.git` / без packaging-манифеста.** Для
  *ручного* пути это нормально — регистрация идёт по записи проекта, а не по
  детекции манифеста: дайте проекту абсолютный `paths[0]` и проиндексируйте.
  *Авто*путь строже: нет манифеста в cwd — нет авторегистрации.
- **Несколько путей у одного проекта?** Граф индексирует первый
  зарегистрированный путь (`paths[0]`) — один корень, один граф на проект.
- **Корень проекта перенесли на диске.** Регистрация становится призраком:
  `vesma_list_graph_projects` показывает `root_missing: true`, индексация
  отказывает. Чинится командой `vesma graph repoint <project> <new-root>`
  (#450) — устаревший индекс сносится, следующий запуск собирает граф
  заново. Чинить нечего? Призрак удаляется целиком: `vesma graph delete
  <project> --force --confirm-name <project>`.
- **Файл изменился после индексации.** Сниппеты вернутся с маркером `stale`
  вместо содержимого; переиндексируйте (или пусть это делает watch-опрос),
  чтобы обновить.
- **Как выключить всё?** `code_graph.enabled: false` — инструменты отвечают
  `disabled`, маячок прячется, ничего не индексируется. Нужны ручные
  инструменты, но без фоновой автоматики? `code_graph.auto_index: false`.
- **Нужен ли бэкап `code_graph.db`?** Нет. Это перестраиваемый sidecar в
  data dir; `vesma_delete_graph_project` удаляет только индекс, но не
  сущность проекта и не его памяти.
