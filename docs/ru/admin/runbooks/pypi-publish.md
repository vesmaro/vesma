# Runbook: Публикация в PyPI

**🌐 Language / Язык:** [English](../../../en/admin/runbooks/pypi-publish.md) · Русский

Пайплайн публикации пакета `vesma` в PyPI — построен в issue #122,
ADR-0017 Фаза 0 (Distribution) для первой публикации и теперь служит
также штатным пайплайном обновлений. GitHub Actions заблокирован
по billing (#117), поэтому весь пайплайн выполняется локально через
`scripts/pypi-publish.sh` (который с 2026-10-05 отвечает и за container-образ:
в `--publish` он выстраивает ОБЯЗАТЕЛЬНУЮ image-фазу вокруг загрузки —
реализована в одном месте, `scripts/image-publish.sh`; см.
[Container image](#container-image--обязательная-половина-поезда)).

**Загрузки — выполняемые владельцем шаги.** Имена и версии на
PyPI неизменяемы: опубликованную версию невозможно перезалить или
заменить, а имя проекта нельзя тихо перенести. Всё ниже готовит и
проверяет артефакты — сам `twine upload` это осознанный, ручной шаг.

## Каналы PyPI — АКТИВНЫЙ: `vesma` (основной; перепроверено на поезде 5.6.2, оба живых канала несут 5.6.2, mirror заморожен на 5.2.0)

Имя дистрибутива, выбранное 2026-09-01 — `mnemos-memory-server`. В
ребрендинге 5.0.0 каналы публикации переехали: голый слот `vesma` — наш
и является основным каналом (`pyproject.toml` `name = "vesma"`),
`vesma-memory-server` — живое зеркало, а доребрендинговый
`mnemos-memory-server` остаётся опубликованным, заморожен на 5.2.0 до
deprecation. У всех трёх summary «(Vesmaro Project)».

С 5.0.0 импортируемый пакет — `vesmaro` (компат-шим `mnemos` всё ещё
поставляется), CLI: `vesmaro` (канонический), `vesma` (короткий хук) и
`mnemos` (устаревший алиас). Отличаются только устанавливаемое/PyPI-имя
и имя python-импорта. Начиная с поезда 5.5.0 пайплайн публикует ОБА
живых канала одним прогоном: `scripts/pypi-publish.sh` читает основное
имя из `pyproject.toml`, затем подставляет имя зеркала (пересборка +
гейты на каждый дист) и восстанавливает `pyproject.toml` байт-в-байт —
бывший ручной танец с зеркалом кодифицирован в скрипте.

| Канал | Статус на PyPI | Используется |
| --- | --- | --- |
| `vesma` | наш, живой (5.0.0 → 5.6.2) | основной — `pip install vesma`, бейдж README |
| `vesma-memory-server` | наш, живой (5.0.0 → 5.6.2) | зеркало; `scripts/install.sh` сначала опрашивает `vesma`, зеркало — только fallback с предупреждением |
| `mnemos-memory-server` | наш, заморожен на 5.2.0 | доребрендинговый канал, живёт до deprecation |

Исходная матрица решения 2026-09-01 сохранена как записано в тот день
(примечание: её строка `vesma` не совпадает с сегодняшним состоянием
PyPI — см. проверенную таблицу выше; `v0.1.1` в списке релизов нет):

| Имя | Статус на PyPI (2026-09-01, как записано) | Чем занято |
| --- | --- | --- |
| `vesma` | ❌ записано занятым (v0.1.1) | "Memory for agentic AI" — Tyson Chan |
| `mnemos-memory` | ❌ занято (v0.6.0) | "Biomimetic memory architectures for LLMs" |
| `mnemos-memory-server` | ✅ свободно тогда | — выбрано первым, заморожено на 5.2.0 после ребрендинга |
| `vesma-server` / `vesma-mcp` / `vesma-ai` / `vesma-agent-memory` | ✅ свободно тогда | — |

Как перепроверить (без авторизации):

```bash
# 404 = имя свободно, 200 = занято
curl -s -o /dev/null -w '%{http_code}\n' https://pypi.org/simple/<name>/

# чем занято имя
curl -s https://pypi.org/pypi/<name>/json | python3 -c \
  "import json,sys; i=json.load(sys.stdin)['info']; print(i['version'], '|', i['summary'])"
```

Оговорки:

- **Нормализация PEP 503** — `vesma-memory-server`,
  `vesma_memory_server` и `vesma.memory.server` это ОДНО имя на PyPI.
  Проверять надо в нормализованной форме.
- **Фильтр против тайпсквоттинга** — PyPI отклоняет регистрацию имён,
  схожих до путаницы с популярными пакетами. Порог считается на стороне
  сервера; финальное подтверждение любого имени происходит только при
  первой загрузке. Если отклонили — берите следующий кандидат из
  матрицы выше.

**Смена имени** была однострочной правкой (`name = "..."` в
`pyproject.toml`) и пересборкой: `scripts/pypi-publish.sh` читает имя из
`pyproject.toml` и подстраивается автоматически (включая нормализацию
имени файла wheel). Это окно закрыто: `vesma` опубликован, имя закреплено
навсегда (см. правила неизменяемости) — новое имя означало бы новый,
параллельный проект.

> **Примечание про артефакты (2026-09-01):** тег `v3.1.0` нарезан со
> старым именем и НЕ пере-нарезается (его npm-канал `pi-mnemos@3.1.0`
> уже опубликован). Wheel-артефакта с новым именем файла для v3.1.0 не
> существует — маркер `<!-- version:pip -->` в README поэтому указывает
> на СЛЕДУЮЩИЙ релиз (v3.2.0). `scripts/sync-readme-version.sh` держит
> маркер корректным начиная с этого релиза; `scripts/install.sh`
> строит URL из нормализованного имени файла.

## Пайплайн — `scripts/pypi-publish.sh`

| Режим | Что делает |
| --- | --- |
| по умолчанию (check) | CL changelog-префлайт + гейты G0–G4, сборка wheel/sdist, `twine check`, офлайн metadata-smoke — для КАЖДОГО диста-кандидата |
| `--dists "a b"` | ограничить список дистов (по умолчанию: `vesma vesma-memory-server`; env-оверрайд `CANDIDATE_DISTS`) |
| `--full-smoke` | дополнительно ставит каждый wheel С зависимостями в одноразовый venv, запускает `vesma --version` (нужен pypi.org) |
| `--publish` | image-префлайт + сборка + smoke, затем `twine upload` на каждый дист, затем image push + анонимная проверка (нужны release-тег, учётные данные PyPI И `GHCR_TOKEN`; пути пропуска image-фазы НЕТ) |
| `--publish --full-smoke` | рекомендуемая комбинация перед загрузкой |
| `--i-own-name` | обязателен для загрузки, когда проект на PyPI уже существует (обновления ТОЛЬКО нашего проекта) |
| `--reuse-dist` | пропустить сборку, если в `dist/<имя>/` уже лежат подходящие артефакты |
| `--dry-run` | напечатать все шаги, ничего не менять (работает без `.venv`) |

Алиас в Makefile: `make pypi-publish` (check-режим).

### Механика мульти-диста (кодификация поезда 5.5.0)

Для каждого диста-кандидата скрипт переписывает `[project] name` в
`pyproject.toml` (бэкап + ловушки `EXIT`/`INT`/`TERM`), пересобирает в
изолированный `dist/<нормализованное-имя>/` и повторяет гейты.
Восстановление проверяется `git diff` после каждой подстановки —
неудачное восстановление это жёсткая ошибка, поэтому `pyproject.toml` не
может остаться изменённым даже при падении посреди прогона. Остаточный
`pyproject.toml.pypi-publish.bak` от убитого прогона отказывается на
старте. Дисти-зеркала разделяют импортируемый пакет (`vesmaro`) и CLI
точки входа — отличается только имя дистрибутива.

### Гейты

| Гейт | Проверяет | Жёсткий отказ? |
| --- | --- | --- |
| CL | changelog-префлайт: в `[Unreleased]` CHANGELOG.md меньше 3 содержательных строк, а с прошлого тега накопились коммиты → `WARN` (никогда не блокирует) | никогда |
| G0 | имя на PyPI per dist: 404 = свободно (первая публикация); 200 + `--i-own-name` = обновление; целевая версия уже на PyPI = всегда ошибка | режим `--publish` |
| G1 | HEAD ровно на release-теге `vX.Y.Z` (один раз) | режим `--publish` |
| G2 | версия тега == версия в `pyproject.toml` (один раз) | режим `--publish` |
| G3 | версии в именах wheel + sdist == версия в `pyproject.toml` (per dist) | режим `--publish` |
| G4 | версия установленного в smoke-venv пакета == версия в `pyproject.toml` (per dist) | всегда (доказательство артефактом) |

G4 проверяет пост-ребрендинговую раскладку wheel: ресурс-чеки идут по
установленному пакету `vesmaro` (`integrations/`, `scripts/`), а не по
устаревшему шиму `mnemos`.

G0 остаётся жёстким предохранителем теперь, когда проект живой: пересборка
уже опубликованной версии чисто падает ЕЩЁ ДО попытки загрузки (версии
неизменяемы — поднимайте версию и пересобирайте), а `--publish` при
несовпадении имени/версии с нашим проектом отклоняется без
`--i-own-name`.

## Container image — обязательная половина поезда

Директива владельца 2026-10-05 (карта `vesma-ghcr-5x-parity`; повод —
образы 5.3.0 / 5.4.0 / 5.5.0, которых на ghcr.io не оказалось):
**образ появляется синхронно с каждым релизом.** В `--publish` поезд
прогоняет image-фазу БЕЗ пути пропуска — флага `--no-image` больше нет,
а отсутствие билдера или учётных данных — жёсткий отказ поезда, а не
тихий шаг в сторону.

Порядок (осознанный):

1. **Image-префлайт** (до первой загрузки) — билдер на месте,
   `GHCR_TOKEN` на месте, трёхсторонний гейт версий.
2. **Сборка + smoke образа** (до любой загрузки) — нерабочее окружение
   образа блокирует весь поезд ДО того, как что-либо опубликовано где-либо.
   Smoke запускает `vesma --version` внутри собранного контейнера и требует
   ровно `vesma $VERSION` в первой строке.
3. **Загрузки PyPI** (без изменений, мульти-дист цикл).
4. **Push образа + анонимная проверка** (после всех успешных загрузок).
   Push идёт через `skopeo copy` с явными транспортами
   (`containers-storage:` → `docker://`; проверено на поезде 5.5.0, где
   `podman push` на ghcr.io падал 403 на первой же blob-проверке, а тот же
   authfile через skopeo работал), с фолбэком на прямой `podman/docker
   push`. Затем анонимная pull-проверка: `tags/list` содержит версию, а
   дайджесты манифестов `:VERSION` и `:latest` равны запушенному.
5. Если push/проверка упали ПОСЛЕ успешной публикации на PyPI, прогон
   заканчивается громким баннером `RELEASE INCOMPLETE` с точной
   командой догоняющего запуска —

   ```bash
   GHCR_TOKEN=<token> scripts/image-publish.sh catch-up
   ```

   — и ненулевым кодом выхода. Опубликованная PyPI-версия без её образа
   никогда не отчитывается зелёным релизом; собранный образ ждёт локально,
   catch-up дозаливает его (ничего больше не трогая).

Гейты версий (VG1–VG3, жёсткие): HEAD ровно на теге `vX.Y.Z`; версия тега
== версия в `pyproject.toml`; в `CHANGELOG.md` есть секция `## [X.Y.Z]`
(changelog-freeze — часть релиза: образа не может существовать для версии,
за которую changelog не ручается). Сборка также перегенерирует
гитигнорированные gRPC-стабы (`scripts/gen-proto.sh`), которые COPY-ит
Containerfile.

Учётные данные и тулчейн:

- `GHCR_TOKEN` — классический PAT со скоупами `repo` + `write:packages`,
  экспортируется в моменте (никогда не пишется на диск или в историю).
  `GHCR_USER` по умолчанию `vesmaro`.
- Билдер: `podman` → `buildah` → `docker` (оверрайд `VESMA_IMAGE_BUILDER`).
  Раннер smoke: `podman` → `docker` (`VESMA_IMAGE_RUNNER`). Пушер:
  `skopeo` (`VESMA_IMAGE_SKOPEO`). В distrobox, где podman живёт на ХОСТЕ,
  переопределите все три одним префиксом, например
  `VESMA_IMAGE_BUILDER="distrobox-host-exec podman"
  VESMA_IMAGE_RUNNER="distrobox-host-exec podman"
  VESMA_IMAGE_SKOPEO="distrobox-host-exec skopeo"` — оверрайд skopeo
  обязателен: он должен разделять хранилище с билдером.
- Логин идёт через свежий временный authfile, shred-ится на выходе; токен
  не появляется ни в аргументах процессов, ни в логах.

`--no-image` и цель `make local-release-no-image` упразднены (цель Makefile
теперь громко падает с указанием на каноническую команду).
`scripts/local-release.sh` (устаревший GitHub-Release fallback) делегирует
оба своих image-шага в `scripts/image-publish.sh` — реализация image-фазы
ровно одна.

## Канон окружения — бутстрап релизного worktree

Бутстрап релизного worktree — ТОЛЬКО lockfile-дисциплиной:

```bash
uv sync --extra dev          # уважает uv.lock — ровно запинненный граф
```

НЕ бутстрапите через `uv pip install -e ".[dev]"` (или `uv pip install`
любой зависимости): он разрешает зависимости заново и ИГНОРИРУЕТ
`uv.lock`. На поезде 5.5.0 это молча утянуло onnxruntime 1.30 (latest)
вместо залоченного 1.27.0, сломало бенч-пин (B1) и увело cosine-инвариант
на 5.4e-4 — инцидент, стоивший повторного прогона quality-гейта. Локфайл
существует именно затем, чтобы каждый worktree собирал одинаковый граф;
осознанное изменение зависимостей идёт через
[ранбук dependency-updates](dependency-updates.md) и пере-лочит
`uv.lock` в review-аемом PR.

## npm-канал — `@vesmaro/vesma` (`packaging/npm/`)

npm-манифест живёт в репо в `packaging/npm/package.json` (легаси
корневой `package.json` — pi-mnemos — заморожен и этим пайплайном не
трогается). Пакет — метаданные/маркер (README + манифест, без JS-кода):
кормит npm-бейдж версии и npm-ногу `vesma update`. Публикация —
шаг владельца, та же философия, что и с PyPI:

```bash
packaging/npm/publish.sh                    # check: гейт версий V1 + staging + npm pack + гейт состава C1 (без загрузки)
packaging/npm/publish.sh --compare-registry # + R1: сравнить локальный состав с метаданными опубликованного диста (WARN)
packaging/npm/publish.sh --publish          # шаг владельца: гейт реестра R0 + npm publish (NPM_TOKEN или ~/.npmrc)
```

Состав детерминирован (C1): ровно `package/package.json` +
`package/README.md`, закреплено allowlist-полем `files`. Опубликованный
5.5.0 сверен 2026-10-05: `README.md` байт-в-байт равен репо-README
(sha256 `7b8400dd…`), поля манифеста равны — опубликованный тарбол нёс
ещё и забытый от ручного `npm pack` мусор `pack-preview.tgz`; этот
артефакт ручного флоу кодифицированный пайплайн НЕ воспроизводит (и
именно поэтому существует гейт состава). Версии на npm тоже
неизменяемы: уже опубликованная версия отклоняет `--publish` (R0).
Версию `packaging/npm/package.json` держите в локстепе с
`pyproject.toml` на каждый релиз — V1 это проверяет.

## Процедура публикации (владелец)

Когда имя выбран и релиз нарезан (`release/X.Y.Z` → `main`, тег
`vX.Y.Z`, см. git-workflow runbook):

1. **Создать API-токен PyPI** — <https://pypi.org/manage/account/token/>.
   Для самой ПЕРВОЙ загрузки проекта ещё нет, поэтому токен должен быть
   account-scoped; сразу после первой публикации удалите его и
   выпустите project-scoped токен для всех последующих загрузок. Токен
   нельзя вставлять в файлы, чат или историю shell — экспортируйте его
   в моменте:

   ```bash
   export PYPI_TOKEN=pypi-...   # из UI PyPI, живёт только в этом shell
   export GHCR_TOKEN=github_pat-...   # классический PAT, repo + write:packages — без него image-фаза откажется работать
   ```

2. **Переключиться на тег и запустить пайплайн целиком** (один прогон
   публикует оба живых канала — `vesma` + зеркало `vesma-memory-server` —
   и container-образ):

   ```bash
   git checkout vX.Y.Z
   scripts/pypi-publish.sh --publish --full-smoke
   # если (и ТОЛЬКО если) проект на PyPI уже существует и наш:
   scripts/pypi-publish.sh --publish --full-smoke --i-own-name
   # ограничить каналы (редко нужно):
   scripts/pypi-publish.sh --publish --dists "vesma"
   ```

3. **Проверка после публикации** (из ЧИСТОГО venv, не dev-ового):

   ```bash
   pip index versions <final-name>            # наша версия должна появиться
   curl -s -o /dev/null -w '%{http_code}\n' https://pypi.org/simple/<final-name>/   # 200
   pip install <final-name> && vesma --version
   ```

4. **Закрыть цикл** — обновить `docs/en/admin/runbooks/install.md` (+ RU
   зеркало) реальной командой `pip install`, упомянуть пакет в notes
   релиза, отметить критерий приёмки «pip install works from PyPI» из
   #122.

## Правила неизменяемости (жёсткие ограничения PyPI)

- **Никогда не перезаливать версию.** Единожды загруженное имя файла
  выгорает навсегда, даже если проект удалить. Ошибка в `vX.Y.Z` →
  поднимите версию до `vX.Y.Z+1` (или `X.Y.(Z+1)`) и загрузите фикс.
- **Никогда не удалять и не пересоздавать проект** ради «сброса» версий.
- Сломанный релиз **yank-ается** (`pypi.org/manage/project/...`), а не
  удаляется — yank-нутые версии всё ещё резолвятся для pinned-установок.
- Переименовать опубликованный проект невозможно — новое имя означает
  новый проект, а старый продолжит существовать.
