# DRAFT: store namespace migration to vesma branding (6.0.0 backlog item #9)

Status: DRAFT for Architectural Committee review. Promoted to an ADR
(0036 or next free) only after a ratified verdict. Nothing here is
implemented; this document exists so the committee evaluates the riskiest
backlog block before the fill queue reaches it.

## Context

The storage layer still carries mnemos-era internals that are invisible to
end users but load-bearing for the product itself:

- tag namespace `mnemos:*` on every stored record (learning, decision,
  checkpoint, no-federate, ...) — the storage data contract;
- store project slugs (`project:mnemos` and friends) — the silo key used
  by recall, awareness, task scoping;
- the canonical config/data home `~/.mnemos/` (config.yaml pins paths per
  device) and the database file name `mnemos.db`;
- the awareness cursors, checkpoint records and run ledgers that reference
  the slugs above.

Live scale on the reference machine: one canonical store (3000+ records),
plus per-project silos; federation peers sync tagged records between
devices. Owner policy: ONE store per device, backups via the SQLite
backup API before risky operations.

6.0.0 (owner ruling 2026-10-03) exists precisely for destructive changes
of this class — but unlike the MCP-tool rename (slice F1), a mistake here
corrupts or orphans live data, and federation makes the blast radius
cross-device.

## Options

**A. Full migration** — tags `mnemos:*` → `vesma:*`, slugs re-siled,
`~/.mnemos` → `~/.vesma`, `mnemos.db` → `vesma.db`, in-place UPDATE sweep
+ FTS reindex + explicit `vesma migrate-store` command.

**B. Split the block**: migrate paths (`~/.mnemos`, db file name — cheap,
mechanical, reversible by directory swap), keep the tag prefix `mnemos:`
as an internal data format indefinitely (documented, not user-facing).

**C. Freeze** — rename nothing; the mnemos internals become a permanent
internal codename (like CPython's or PostgreSQL's internal jargon).

## Risk register (option A)

1. **Federation skews**: a 6.0 store exchanging records with a 5.x peer
   sees `mnemos:` tags as foreign; sync filters, dedup keys and
   no-federate markers must dual-accept during the transition window.
2. **Checkpoint/amnesia cliff**: historical session checkpoints are
   recallable only under their old slug; a rewrite must touch every
   record's tags, or history becomes unfindable (G1 gates depend on it).
3. **Search index**: FTS content includes tags → reindex required;
   vectors are id-keyed (stable) but pipeline_state/provenance lines
   embed slugs.
4. **Tooling coupling**: harness packs, board integrations, eyes curated
   docs and the awareness/swarm code all match on the tag prefix and
   slug spellings — a partial rename is worse than none.

## Draft shape of the migration (if A is ratified)

1. `vesma migrate-store` — explicit command, never auto-run on boot:
   dry-run mode, SQLite backup-API snapshot gate (mandatory target path),
   in-place tag/slug UPDATE, FTS rebuild, post-migration count
   verification, idempotent re-run, loud report.
2. Dual-accept read window on the 6.0 code: accept both `mnemos:*` and
   `vesma:*` on read/filter, write only `vesma:*`. Removed in 6.1 at the
   earliest.
3. Federation: peers negotiate; records with legacy tags are accepted,
   stored, rewritten lazily; sync dedup keys versioned by tag-namespace
   epoch.
4. Path migration rides the same command (dir swap + config repoint),
   after the store snapshot, before tag rewrite; old dir kept renamed
   `~/.mnemos.pre-6.0` until the operator deletes it.
5. Order inside 6.0.0 fill: LAST, on a quiet window, one device at a
   time; boxes staggered after the reference machine proves the run.

## Open questions for the committee

- A vs B vs C (TL lean: **B** — paths are worth migrating, the tag
  prefix is a data format whose rename buys branding nothing users can
  see; but the committee may weigh "clean brand forever" differently).
- If A: single transition release (6.0.0 does it) vs dual-accept across
  6.0–6.1 as drafted.
- Silo slug strategy: rename `project:mnemos` (the main silo) or keep
  silo keys as immutable identifiers with display-name separation.
- Who executes: a dedicated wave with the migration command merged and
  rehearsed on a CLONE of the live store first (store snapshot restore
  drill), never on the live file directly.

---

## Committee verdict (2026-10-03) — ratified recommendation, 3/3 unanimous

**Option B (split)** — migrate user-visible paths, freeze the tag prefix as
storage data format. Positions: Security, System Engineering, Product
Architecture — no disputes between them; each adds conditions.

Security: the `mnemos:no-federate` trust marker (~20 hardcoded enforcement
sites, added by the secrets scanner to exactly the secret-bearing records)
must stay byte-stable — a rewrite across a mixed 5.x/6.0 fleet converts the
trust boundary into an exfiltration amplifier. Crypto/auth constants are
permanently out of scope unless an explicit re-encryption plan exists:
fernet salt `mnemos.api.auth.fernet.v1`, cookie `mnemos_session`,
`/run/mnemos/core.sock`.

System engineering: the mover is `vesma migrate-store`, explicit-only
(never auto-run — the v2.1 `migrate_layout()` auto-run precedent caused
races): resolve config → refuse if both configs exist without `--config` →
quiesce gate (socket live / db lock = refuse) → SQLite backup-API snapshot
to mandatory `--backup` → verify readable + counts → same-FS atomic rename
`~/.mnemos` → `~/.vesma` (cross-FS: copy+fsync+hash) → rewrite pins in
config.yaml + `mnemos.db` → `vesma.db` → idempotence marker → post-checks
(row counts, FTS match, recall of a known checkpoint, one federated pull
vs a live 5.x peer). Discovery chain gains the old-path fallback (new
first, `~/.mnemos` last); zero-config refuses to fork `~/.vesma` while
`~/.mnemos` exists. Clone-rehearsal drill is a ratification precondition.
Also frozen for 6.0: `/run/mnemos` socket, `mnemos-mesh` binary PATH
default (config-pinnable; coordinated Go+Python rename deferred).

Product: the tag prefix is NOT invisible — it faces users in exports,
`--tags` typing, and the tag-contract docs. Therefore B carries:
(1) input alias — `vesma:*` accepted at every typing surface, normalized
to `mnemos:*` on write (users never type the legacy prefix again);
(2) point-of-contact documentation — one standardized line in tag-contract
page, `--tags` help, export schema table ("`mnemos:*` is the canonical
storage prefix, stable by contract; `vesma:*` accepted as alias");
(3) export schema `mnemos_version` → `vesma_version` (import accepts both);
(4) the migrate-store command design above ships even though full option A
is rejected.

Dismissed: **A** — 10–15 days plus a standing dual-accept tax and the
trust-marker rewrite for zero visible gain; **C** — correct for invisible
plumbing, actively harmful at the typed and exported surfaces.

Recommended 6.0.0 framing: "the contract release — everything you touch is
vesma end to end; below the touch surface storage keeps its historical
prefix, frozen and documented, because your data's identity must not churn
with our branding."

Backlog additions (6.0.0 fill): input alias; point-of-contact doc lines;
export `vesma_version` rename; `vesma migrate-store` implementation
(path-only, per the step list) with the clone-rehearsal drill.
