# ADR-0050: MCP-плоскость — HTTP-эндпоинт в ядре и эволюция к компоненту-фронту

- Статус: Ratified (владелец «Погнали» 2026-10-31; заочный АрхКом 2026-10-31 — ACCEPT-WITH-CONDITIONS, 2 позиции, свод в спецификации §11)
- Дата: 2026-10-31
- Спецификация: `handoff/spec-mcp-platform-and-store-resilience-20261031.md` (v2)
- База: 6.8.0, main ca22ba8

## Контекст

Каждый харнес сегодня спавнит собственный `vesma mcp-server` (stdio) на сессию: N экземпляров с дрейфом версий (инцидент 2026-10-31: бокс-CLI 6.4.0 без модуля `mcp` против прода 6.8.0), записи минуют инварианты ядра (writer-lock ADR-0049, mint-защита), агентский лейн де-факто второй источник правды (инцидент 29.10: неделя записей мимо прода), изоляции харнесов нет.

## Решение

1. **Целевая форма** — MCP-фронт как компонент платформы (Ф2, манифест в components.d, слот, супервизия), stateless-прокси к ядру; эволюция в два шага: **Ф1** — streamable HTTP эндпоинт `/mcp` внутри ядра (`vesma serve`), **Ф2** — вынос фронта в компонент (триггер старта: второй харнес).
2. **Транспорт** — MCP streamable HTTP (SDK 2.x `StreamableHTTPServerTransport`/`StreamableHTTPSessionManager`); для Ф2 предпочтителен UDS (закрывает класс «локальный импостор на TCP-loopback»); TCP 127.0.0.1 допускается в Ф1 с обязательной аутентификацией.
3. **Аутентификация** — каждое соединение/запрос `/mcp` требует валидный агент-токен (`agent_tokens.validate_agent_token`, fail-closed); **наследование loopback-доверия API на `/mcp` запрещено** — loopback без токена = 401. Ядро скоупит каждый front-originated запрос по токену харнеса (фронт — носитель идентичности, не авторизатор; у фронта нет второго пути записи — пин-тест).
4. **Изоляция харнесов** — по осям идентичность/данные/ресурсы (агент-токены, enforced `agent:<slug>` — расширение mint-protection-класса, per-token квоты), НЕ процессами. Форма «супервизор с детьми на харнес» (Ф3) отклонена АрхКомом; residual «RCE фронта = весь стор в песочнице сервис-аккаунта (SL-18)» фиксируется с триггерами пересмотра (non-loopback бинд, мультиарендный хост, per-harness env-гигиена уровня ОС).
5. **Кросс-чтение по умолчанию** — `published_only` (зеркало awareness cross-silo cap), intersection с project-грантами токена, fail-closed на неизвестное значение конфига.
6. **Token-жизненный цикл** — потолок TTL 24h сохраняется; автоматизация ротации харнес-токенов — условие волны неймспейсов.
7. **stdio-мост** для харнесов без HTTP-транспорта — контракт с W1, реализация в W2.

## Волны

- **W1 (эта волна)**: `/mcp` в ядре + токен-аутентификация + контрактные тесты инструментов по HTTP + флип регистрации zcode; stdio-мост — только контракт; residual «изоляции нет до W3» — явно в отчёте.
- **W2**: компонент-гейтвей (слот, env.d, юнит-санбокс SL-18 без даунгрейдов, порт в реестре компонентов, спул-роль в FHS-манифесте).
- **W3**: неймспейсы и квоты (enforced agent-tag на всех сёрфейсах с пин-тестами, переопределяемые per-token лимиты, DR-25).
- **W4**: resilience (ADR-0051): спул, машина состояний, TTL, signage (DR-24).
- **W5**: флип флота, упразднение лейн-записи, `vesma lane ingest`, доки EN/RU.

## Отклонённые альтернативы

- Статус-кво (N stdio-экземпляров) — дрейф версий, обход инвариантов, отсутствие изоляции.
- Ф3 (процесс-на-харнес) — изоляция достигается дешевле на уровнях идентичности/данных/ресурсов; процессное дробление не даёт ни namespace-, ни cgroup-семантики.
- Кластеризация фронта — фронту нечего кластеризовать (stateless); точка отказа — хранилище (ADR-0051 + mesh).
- Консенсус-репликация стора (raft-класс) — отдельный будущий трек; mesh уже даёт асинхронную мульти-машинность метаданных.

## Последствия

- Харнесы переводятся с локального SQLite на HTTP-клиента ядра: латентность +1 локальный прыжок, зависимость от живого `serve` (осознанно; resilience — W4).
- Единый источник правды: записи идут через writer plane ядра со всеми инвариантами.
- MCP-поверхность инструментов (`vesma_*`) не меняется — меняется только транспорт.
- Номера DR-24/DR-25 резервируются волнами W4/W3; номера ADR — против свежего main.
